## 边界一：客户端提交链路与 ShareDbAdapter.commit 现状

### 1.1 客户端真实提交入口：双重通道架构

**关键发现**：客户端单元格编辑并**不通过 ShareDB OT 路径提交**，而是走 REST API 路径。ShareDB 仅用于接收服务端广播。

#### 证据链 1.1.1 — 前端 Record.updateCell 真实路径

**文件**: `packages/sdk/src/model/record/record.ts:131-168`

```typescript
async updateCell(fieldId: string, cellValue: unknown, localization?) {
  const oldCellValue = this.fields[fieldId];
  try {
    // 本地乐观更新
    this.onCommitLocal(fieldId, cellValue);  // line 138
    this.fields[fieldId] = cellValue;

    // 真实提交：调用 REST API updateRecord
    const [, tableId] = this.doc.collection.split('_');
    const res = await updateRecord(tableId, this.doc.id, {   // line 141
      fieldKeyType: FieldKeyType.Id,
      record: {
        fields: {
          [fieldId]: cellValue === undefined ? null : cellValue,
        },
      },
    });

    // 计算字段/附件字段服务端返回值同步
    this.updateComputedField([...fieldsToSync], res.data);  // line 158
  } catch (error) {
    // 回滚本地
    this.onCommitLocal(fieldId, oldCellValue, true);  // line 160
    return error;
  }
}
```

**关键调用点证据**:
- `updateRecord` 是 `@teable/openapi` 的 REST API 调用，**不是 ShareDB submitOp**
- `this.onCommitLocal` 仅做本地状态更新 + 触发 UI 重渲染，不发送到服务端
- 失败时本地回滚

#### 证据链 1.1.2 — onCommitLocal 的真实行为

**文件**: `packages/sdk/src/model/record/record.ts:98-111`

```typescript
private onCommitLocal(fieldId: string, cellValue: unknown, undo?: boolean) {
  const oldCellValue = this.fields[fieldId];
  const operation = RecordOpBuilder.editor.setRecord.build({
    fieldId,
    newCellValue: cellValue,
    oldCellValue,
  });
  this.doc.data.fields[fieldId] = cellValue;  // 直接修改 doc.data
  this.doc.emit('op batch', [operation], false);  // 触发本地事件
  if (this.doc.version) {
    undo ? this.doc.version-- : this.doc.version++;  // 本地版本号自增
  }
  this.fields[fieldId] = cellValue;
}
```

**证据**: `emit('op batch', ..., false)` 第三个参数 `false` 表示这是**本地事件**，不会通过 ShareDB 发送到服务端。

#### 证据链 1.2.2 — 为什么未实现不影响功能

ShareDB 标准生命周期中 `commit` 的作用是**持久化 ops 到数据库**。但 Teable 采用了「PostgreSQL 作为唯一真相源」的架构：

1. **所有写入走 REST API → Command Handler → 数据库事务**，不走 ShareDB 提交路径
2. ShareDB 仅作为广播通道，通过 `getSnapshot()` 从数据库读取实时状态
3. `getOps()` 不是从 ops 历史表读取，而是**从快照动态生成虚拟 ops**（见边界四）

**调用点证据**: 服务端变更通过 `ShareDbBackendPublisher` 直接调用 `doc.submitOp()` 走服务端内部连接，不经过 `commit`。

## 边界二：@@v2-projection 豁免与 record 限制的判定顺序

### 2.1 onSubmit 中间件精确判定顺序

**文件**: `apps/nestjs-backend/src/share-db/share-db.service.ts:191-226`

```typescript
private onSubmit = (context, next) => {
  // 判定 1: options.source === '@@v2-projection'
  const submitSource = context.options?.source ?? context.extra?.source;
  if (submitSource === v2ProjectionSubmitSource) {
    return next();  // 豁免 1：直接放行
  }

  // 判定 2: op.src.startsWith('@@v2-projection:')
  const opSource = typeof context.op.src === 'string' ? context.op.src : '';
  if (opSource.startsWith(v2ProjectionOpSourcePrefix)) {
    return next();  // 豁免 2：直接放行
  }

  // 判定 3: 非客户端流（无 WebSocket 连接）
  if (!hasClientStream(context.agent)) {
    return next();  // 豁免 3：直接放行
  }

  // 判定 4: 客户端限制 — 仅允许 Record 编辑
  const [docType] = context.collection.split('_');
  if (docType !== IdPrefix.Record || !context.op.op) {
    return next(new Error('only record op can be committed'));  // 拒绝
  }

  next();  // 放行合法的客户端 Record op
};
```

### 2.2 判定顺序的精确证据

| 顺序 | 判定条件 | 代码行 | 结果 |
|------|---------|-------|------|
| 1 | `options.source === '@@v2-projection'` | line 204-206 | ✅ 豁免 |
| 2 | `op.src.startsWith('@@v2-projection:')` | line 208-211 | ✅ 豁免 |
| 3 | `!hasClientStream(agent)` | line 213-215 | ✅ 豁免 |
| 4 | `docType === Record && op.op 存在` | line 217-222 | ✅ 放行 / ❌ 拒绝 |

**短路逻辑**: 四个判定是 `if-return` 顺序，命中前面的豁免则直接 `next()`，后面的判定不执行。

### 2.4 客户端 Record 限制的实际意义

**判定条件**: `docType !== IdPrefix.Record || !context.op.op`

**真实含义**:
- `docType !== Record`: 禁止字段/视图/表的客户端直接修改
- `!context.op.op`: 禁止无操作内容的空提交

**代码证据**: `IdPrefix.Record` 是字符串常量 `'rec'`，匹配集合名如 `rec_tblabc123`。

**修正此前推断**: 客户端实际上**从不通过 ShareDB 提交任何修改**（见边界一），所以这条限制在当前实际运行中是**死代码**，仅作为防御性编程存在。

```typescript
const shouldRefreshAfterProjectedMutation = (tableId, batch, actionKey) => {
  for (const item of batch) {
    const action = item as ActionTrigger;
    if (action.actionKey !== actionKey) continue;

    const payload = toLargeProjectedMutationPayload(tableId, action.payload);
```

2. 检查是否是流式 chunk

### 4.2 internalGetOps 版本回补算法的精确步骤

**文件**: `apps/nestjs-backend/src/share-db/share-db.adapter.ts:336-412`

```

输出: ops[]
```

### 4.3 getOpsFromSnapshot 的精确转换规则

**文件**: `apps/nestjs-backend/src/share-db/share-db.adapter.ts:517-550`

```typescript
private getOpsFromSnapshot(docType, snapshot): IOtOperation[] {
  switch (docType) {
    case IdPrefix.Record:
      // 遍历 record.fields，为每个字段生成 setRecord op
      return Object.entries((snapshot as IRecord).fields).map(([fieldId, fieldValue]) => {
        return RecordOpBuilder.editor.setRecord.build({
          fieldId,
          newCellValue: fieldValue,
          oldCellValue: undefined,  // ⚠️ 关键：无 oldValue
        });
      });
    case IdPrefix.Field:
      // 遍历 field 属性，过滤掉 id，生成 setFieldProperty op
      return Object.entries(snapshot as IFieldVo)
        .filter(([key]) => key !== 'id')
        .map(([key, value]) => {
          return FieldOpBuilder.editor.setFieldProperty.build({
            key: key as IFieldPropertyKey,
            newValue: value,
            oldValue: undefined,  // ⚠️ 关键：无 oldValue
          });
        });
    // ... Table 类似
  }
}
```

**关键证据**: 所有回补 op 的 `oldCellValue`/`oldValue` 均为 `undefined`，意味着**不做冲突检测**，直接覆盖。

### 4.5 版本回补的风险边界

**已证实的风险点**:

1. **静默覆盖**: `oldValue: undefined` 导致如果客户端有未提交的本地修改，回补 op 会直接覆盖（虽然客户端实际上从不通过 ShareDB 提交）

2. **最后一个 op 有效**: gap 填充中只有最后一个 op 携带真实操作，前面的都是空 op。这意味着：
   - 客户端应用 `gapVersion` 个 op，但前 `gapVersion-1` 个不改变状态
   - 版本号单调递增，保证客户端版本链不断裂

3. **删除文档不回补**: `hasGapVersion()` 对 `RawOpType.Del` 返回 false，删除的文档不生成回补 ops
